# Production incident playbook

Use [operations evidence rules](production-operations.md) and
[support escalation](support-escalation.md) for every row. Procedures are for an
explicitly authorized production operator. No test writes or automatic retries.

## Common response and recovery gate

Open a restricted case: severity, UTC start/last healthy time, deployment/SHA,
affected scope, request IDs, safe error codes and impact. Check health/readiness
and correct-deployment runtime logs. If a response is lost, refresh authoritative
state before deciding whether a command failed; HTTP status alone does not prove
commit outcome. Never create a fresh idempotency key for an ambiguous retry.
Do not capture credentials or business payloads in shared notes.

Escalate total outage, cross-tenant exposure or authoritative corruption as P0
immediately; critical workflow failure as P1 immediately; recoverable degradation
as P2 with a named owner/next update. These are triage rules, not measured SLOs.
No pager or staffed response time is verified.

Recovery for every row requires the exact deployed SHA/alias, health/readiness,
authorized affected-user read smoke, absence of recurring errors during the
observation window and review of audit/duplicate/partial effects. Actual business
commands require separate operator authorization. Keep the incident open for
unresolved financial or security impact.

Do not use failure-provoking or write-based monitoring stimuli in production.
Reproduce denial, finance and concurrent-write scenarios on an approved isolated
synthetic environment, preserving equivalent PostgreSQL version/ownership/UTC.
