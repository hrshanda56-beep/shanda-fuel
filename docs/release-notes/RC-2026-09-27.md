# Shanda Fuel release candidate notes

**Candidate:** current RC at integration tip `6b85ae5`
**Repository version:** `0.1.0`
**Date:** 2026-09-27
**Decision status:** ready for authenticated staging verification; not yet a pilot or production approval

## Summary

This RC is the current merged modular-monolith baseline for the integrated
forecourt, reconciliation, inventory, cash, supplier, customer, provider
settlement, reporting, costing, daily-operations, and security slices. It also
contains the release-hardening integration and Security Wave 1 step-up/MFA
establishment already merged on `main`.

This document is a release draft. It records repository evidence and the gates
that still require an operator with staging and provider access. It does not
claim that a staging deployment, restore drill, performance run, or pilot exit
has completed.

## Included in this RC

- Tenant-aware application, authorization, PostgreSQL RLS, runtime-role
  separation, signed audit events, idempotency, and fail-closed tenant context.
- Daily station operations and reconciliation through submit, return, approve,
  post, and lock, with server-owned exact-decimal calculations.
- Inventory movement, opening/receipt valuation, canonical ordinary-fuel sale
  revenue, WAC/COGS attribution, and whole-history late-cost revaluation.
- Cash collections/deposits/manual bank confirmation, supplier creditors,
  customer credit/prepaid subset, and provider settlement reconciliation with
  named allocation reversal.
- A10 management/operational reporting and ordinary-fuel gross-margin read
  model. This is not a general ledger, statutory P&L, tax engine, or export
  system.
- A11 daily operations composition with truthful draft, loading, error,
  conflict, permission, and downstream-state presentation.
- Better Auth password reauthentication plus TOTP step-up establishment,
  tenant-bound assurance, short-lived expiry, and authenticated setup routes.

## Repository verification

The repository CI gate is defined in
[`/.github/workflows/ci.yml`](../../.github/workflows/ci.yml) and covers:

1. frozen dependency installation and PostgreSQL 16 service;
2. database-role bootstrap and canonical migration application;
3. formatting, lint, typecheck, migration consistency, unit/integration tests;
4. production build and Playwright browser tests.

The merged RC also has focused security step-up/MFA tests and the existing
cross-module integration/E2E coverage. The release owner must attach the CI run
for `6b85ae5` to the release record; this documentation change does not invent
or replace CI evidence.

## Required staging gate before pilot or production

Run [`release-readiness.md`](../release-readiness.md) and the linked
runbooks against the deployed staging URL with synthetic data. The gate is
intentionally deferred until staging credentials, the staging deployment URL,
provider access, and an approved operator are available. The deferred items are
listed explicitly so they are not mistaken for merged implementation.

## Known limitations and follow-ups

- Inventory pools/transfers, calibration execution, interrupted delivery flow,
  full cash custody, customer invoices/benefits/policies, expenses, exports,
  report artifacts, full `as_of`, Action Center, and broader profitability are
  outside the current merged slice.
- Full offline synchronization, conflict merging, bank/provider APIs, GL/tax
  behavior, and historical revenue backfill remain out of scope or deferred.
- Production monitoring integration, backup-provider configuration, restore
  drill evidence, tenant-recovery exercise, and staging performance evidence
  remain operational follow-ups.
- Key-rotation and tenant-scoped recovery procedures still need provider- and
  owner-specific execution details before a pilot is signed off.

## Release decision

The RC may proceed to controlled staging verification. It must not be labeled
pilot-ready or production-ready until the authenticated staging gate, restore
drill, performance verification, security/tenant checks, operational owner
sign-off, and client/accounting/onboarding inputs in the readiness ledger are
complete or explicitly accepted by the responsible owners.
